1背景：H3 每段都要重新编码

MiniMax H3 视频生成中，每一段视频的 conditioning 都由 Qwen3-VL-32B 文本编码器生成——它把 prompt + 参考图 混合编码为一组 hidden states，喂给视频扩散模型（DiT）。32B 模型在 16GB 显存的机器上放不下，只能 CPU 推理。

问题：参考图跨段不变，但 LLM 每段把整条混合序列重新前向一遍——图片 token 占序列 90%+，计算大量重复。已有 VIT 缓存只省视觉编码器，LLM 50 层前向仍是主耗时（单段 ~5 分钟）。

3核心洞察：为什么图片 KV 可以缓存

  • 因果注意力：`Llama2_.forward` 无条件构造 causal mask（triu(1)）——token 只能 attend 它前面的 token；
  • 图片在 prompt 之前：参考图块只 attend 固定的模板/标签文本与其他参考图；
  • mrope 位置固定：图片区间的 3 维旋转位置编码只由 (start, grid) 决定，与后面的文本无关。
// 层 l 的图 token 输出 = f(图 token 输入, 前缀 KV)
himg(l+1) = layer_l( himg(l),  KV前缀(l) )
KV前缀(l) = f(模板, 图1..图N 特征)   ← 跨段不变
→ himg(l) 与 KVimg(l)  ⟂  first_frame / prompt
合成验证：同一组图、不同文本（长度也变），图区间的 KV 与每层输出 hidden 逐位一致（diff = 0）——缓存是数学上成立的，不是近似。

4关键约束：为什么不能逐图独立缓存

图 2 在 layer 0 的输入是自己的 embeds（可独立）；但 layer 1+ 的输入 = 上一层输出，其中图 2 token 的 attention 输出来自它对前缀 KV（含图 1）的查询 → 图 2 的每一层 KV/hidden 都依赖图 1。

图 1 区间 · 可缓存
只依赖固定模板
↓
图 2 区间 · 依赖图 1
key 必须含图 1 指纹 → 等价于前缀并入区间
↓
图 3 区间 · 依赖图 1 + 图 2
逐图拆分无收益，只是文件更碎

推论：任何一张参考图变化 → 其后所有缓存必然失效（架构决定）；"固定段 + 可变段"二分就是理论最大可缓存范围。

5缓存设计：区间、key、拆层存储

5.1 缓存区间：排除末图（first_frame 分离）

缓存区间 = [首图 start, 倒数第二图 end) —— H3 约定 first_frame 总是最后一张（also_ref_first_frame 追加为最后 Picture）。first_frame 每段变 → 重算；前 N-1 张固定 ref 图独立缓存 → 每段命中。单图/无图 → 不缓存。

5.2 key 设计

key = md5( 区间 embeds 字节 ) + "_" + start + "_" + ref 图 grid 摘要
// 命中条件：前 N-1 张图 + 前缀布局位级一致；末图（ff）与 prompt 不在 key 中

5.3 缓存内容：KV + hidden 双份，拆层存储（v2）

字段内容单层大小
k / v每层图区间 K/V（rope 后，最终形态）(1, 8, L, 128)~10MB
h每层图区间输出 hidden（deepstack 注入后）(1, L, 5120)~60MB

存储：h3_kv_cache/<key>/00.pt … 49.pt——每层一个文件，HIT 时逐层惰性加载、用完即弃，峰值内存仅单层 ~70MB（v2 核心改进，见 §8）。

6命中路径：分段 prefill 的实现

输入 x（全序列）
图区间先填充缓存 h[i-1]（第 1 层除外，用真实 embeds）
↓
1 · 本层缓存按需加载（磁盘单层文件）
k / v / h 三个张量，用完即弃
↓
2 · q/k/v 投影 —— 只对文本行
前缀 [0, start) + 后缀 [end, seq)，图区间不投影
↓
3 · KV 组装
cat( 前缀 KV, 缓存图 KV, 后缀 KV )
↓
4 · attention —— 优化内核（flash）
文本行 q × 全 KV（cross-attention 语义）
↓
5 · 输出组装
文本行 = 真值；图区间 = 缓存 h[i]；跳过 deepstack 注入
↓
最后一层 —— 不跳过
conditioning 需要图区间 hidden 真值输出给 DiT → 全量计算（KV 与缓存位级一致）
// llama.py — Attention._forward_segmented（核心）
text_idx  = [0..start) ∪ [end..seq)
xq/xk/xv  = proj(hidden[text_idx])                    // 图区间不投影
xk = cat( xk_text[:, :, :start], cached_k, xk_text[:, :, start:] )
out = optimized_attention( xq, xk, xv, mask=seg_mask, enable_gqa=True )

7未命中路径：KV 的保存

  • 自建 past_key_values：encode 路径（SDClipModel）默认不传 past_key_values → Attention 不返回 KV。保存模式下由 Qwen3VL.forward 自建（batch=1，容量=序列长）；
  • 每层 Attention 把 KV 写进预分配 cache 并回传 → slice 区间；层循环同时收集每层输出 hidden 的图区间；
  • 拆层写盘（每层一个 .pt，原子替换）。
契约陷阱：带回 KV 后 Llama2_.forward 返回 3 元组，但 SDClipModel 把第 3 个元素当 pooled 输出解包 → 必须在 Qwen3VL.forward 还原成 2 元组（KV 已存入 _saved_image_kv）。

8v2 修复：swap 之谜与逐层加载

现象：v1 实装后 HIT 路径 CPU 利用率只有 ~60%，耗时与非缓存几乎相同——独立测试明明省了 92s。

根因（数据链）：

证据值指向
页面文件峰值72.5GB跑 H3 时内存爆 → swap
可用内存3–8GB / 49GBComfyUI --lowvram 占 28GB
v1 HIT 加载整包 torch.load 8.5GB 进内存直接挤爆 → 换页

机制：CPU 拉不满 = 进程在等内存换页（数据被换到页面文件，等磁盘比等内存慢 100–1000 倍）。省下的计算时间被换页等待填满 → 耗时不变。这不是内存带宽饱和（那在反量化阶段是正常且高效的），而是容量不足导致的磁盘等待。

修复：缓存拆层存储 + 逐层惰性加载——HIT 峰值内存 +8.5GB → +70MB，swap 不再被触发。

修复后验证：MISS 325.8s → HIT 223.8s（省 102s，31%），输出位级一致——独立测试的收益在实装环境下稳定复现。

10开关与限制

# Windows，默认关闭；启动 ComfyUI / h3_runner 前设置
set QWEN3VL_KV_CACHE=1
# 未设置时代码行为与修改前完全一致（零侵入）
  • 命中条件：前 N-1 张图 embeds 位级一致（同图 + 同前缀布局 + 同 start）。ref 图/标签/顺序变化 → 新 key。
  • 单图不缓存；段 1（纯 3 ref）少缓存第 3 张（~30–40s，每部电影一次）。
  • 旧格式作废：v1 单文件缓存（<key>.pt）不命中，可删除（56GB）。
  • CPU 反量化固定成本未触及（~25s/次）；进一步提速需 int8 权重（与 KV 缓存正交，且先保证内存充足）。
  • 数值：flash 分段路径与正常路径位级一致；原生 matmul fallback 差异 ~8e-5（bf16 噪声）。
  • 生效：改 qwen3vl.py/llama.py 后需重启进程。
一句话总结：因果注意力 + 图片在前 + 前缀固定 → 图区间每层 KV 与 hidden 独立于文本 → 缓存"固定段"（前 N-1 张参考图），重算"可变段"（first_frame + prompt），分段 prefill 只计算文本行，最后一层保持全量；拆层存储保证内存压力下收益不丢失。
